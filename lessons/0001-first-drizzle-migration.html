Lesson 01 · RunMax API · Drizzle + PostgreSQL

Your first migration is blocked — and package.json is not the problem

You asked what your Drizzle setup is missing. I audited apps/api, ran the tooling against your real database, and found three blockers. This lesson: know exactly what they are, fix them, and understand what comes after setup.

The win

By the end, pnpm db:generate writes apps/api/drizzle/0000_*.sql, and you can predict — before running it — the two errors db:migrate would hit on your PostgreSQL 16 and why.

1 · What is actually missing

Your package.json is complete. drizzle-orm, drizzle-kit, pg, @types/pg, dotenv are all present and installed. The blockers live one level up: in the config, the schema, and the environment.

Blocker 1 — drizzle.config.ts points at a file that does not exist

Your config says schema: "./drizzle/schema.ts", but there is no drizzle/ directory. Your tables live in src/lib/db/schema.ts. I ran your script and it failed exactly there:

Observed — pnpm --filter @repo/api db:generate
Error  No schema files found for path config ['./drizzle/schema.ts']
Error  If path represents a file - please make sure to use .ts or other extension in the path

Blocker 2 — two schema bugs that only surface at migrate time

generate never validates your SQL against PostgreSQL. I tested both statements on a throwaway database on your running server (PostgreSQL 16.15):

Observed — default uuidv7() on your users table
ERROR:  function uuidv7() does not exist
HINT:  No function matches the given name and argument types.
Observed — passwords.user_id char(26) referencing users.id uuid
ERROR:  foreign key constraint "t3_t2_id_fkey" cannot be implemented
DETAIL:  Key columns "t2_id" and "id" are of incompatible types: character and uuid.

uuidv7() is a built-in PostgreSQL function only from version 18 onward; your docker-compose.yaml pins postgres:16-bookworm. The char(26) on passwords.userId looks like a ULID leftover — the referenced users.id is a uuid, and PostgreSQL refuses to enforce a foreign key across those types.

Blocker 3 — environment wiring

  • apps/api/.env does not exist. Your dev script passes --env-file=.env, and dotenv/config in drizzle.config.ts resolves .env against the working directory — apps/api/. Only the repo root has a .env.
  • The postgres image initializes from POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB, not the DATABASE_* names in your .env.example. As written, the container gets no database, user, or password.
Also noted: the empty stubs modules/auth/schema.ts (import {}) and modules/user/schema.ts (empty) are dead weight today. Either delete them or move table definitions there later — one source of truth for drizzle-kit.

2 · The fix

apps/api/drizzle.config.ts
  schema: "./drizzle/schema.ts",
  schema: "./src/lib/db/schema.ts",
apps/api/src/lib/db/schema.ts
  userId: char("user_id", { length: 26 })uuid("user_id")
    .notNull()

Then pick an ID strategy. This is a real decision, not a bug — you wrote uuidv7() for time-sortable keys, which is a good instinct:

OptionChangeTradeoff
Upgrade the imagepostgres:18-bookwormKeeps your schema as written. My recommendation for a greenfield project.
Generate in the appv7 UUID in Node, drop the SQL defaultWorks on any PG version; IDs exist even outside SQL.
Use v4default(sql`gen_random_uuid()`)Zero migration pain; loses time-ordering.

3 · What comes after setup

  1. Create apps/api/.env from .env.example, and add POSTGRES_USER/POSTGRES_PASSWORD/POSTGRES_DB for the container. Then docker compose up -d database.
  2. pnpm db:generate — expect Your SQL migration ➜ drizzle/0000_….sql. I confirmed this output appears once blocker 1 is fixed. Read the SQL: it is exactly what will run against your database. Commit it.
  3. pnpm db:migrate — applies the SQL and records it in the __drizzle_migrations table. First run should print success; run it twice to see the second run do nothing.
  4. pnpm db:studio — open the browser UI and confirm users and passwords exist with the right column types.
  5. Prove the connection in code — make /health run select 1 through db instead of returning static JSON. A health endpoint that never touches the database is not a health endpoint.
  6. Then build features — auth/users modules consume the schema; add db:push to package.json for throwaway prototyping alongside generate/migrate.
Expectation

Steps 2–4 will only go smoothly after you fix all three blockers. If you skip the char(26) fix or the ID decision, db:migrate fails mid-migration with exactly the errors shown above — and a half-applied migration needs cleanup before you rerun.
